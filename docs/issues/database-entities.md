# Чернетка issue

## Назва
Моделі станції, зв’язки EF Core та міграція SQLite зі збереженням даних

## Опис
Зараз база містить лише прилади. У відповідях API номер станції та пріоритет підставляються як 1, а дозвіл Smart Grid помилково використовує поле поточного стану приладу.

Додати SolarStation, Equipment і TelemetryLog, зв’язати їх зі станцією та забезпечити збереження пріоритету й дозволу автоматичного керування. Оновлення бази має зберігати наявні прилади: їхні ID, назви, потужність і стан.

Старі прилади, для яких раніше не зберігалася станція, переносяться до імпортованої станції з UserId `legacy-unassigned`. Це технічна позначка невизначеного власника, а не обліковий запис або дозвіл доступу.

## Критерії готовності
- [ ] API успішно збирається.
- [ ] Міграції застосовуються до нової SQLite БД.
- [ ] Оновлення старої БД зберігає прилади та встановлює коректний зв’язок зі станцією.
- [ ] Повторне застосування міграцій не змінює схему.
- [ ] Модель EF Core відповідає останній міграції.
- [ ] Сервіс зберігає і повертає справжні SolarStationId, Priority та IsSmartGridEnabled.
- [ ] Зміна дозволу Smart Grid не змінює IsActive.
- [ ] Неіснуюча станція дає HTTP 400 із помилкою валідації.
- [ ] БД відхиляє неправильні кути, координати, пріоритети та зовнішні ключі.
- [ ] Видалення станції каскадно видаляє її обладнання, прилади й телеметрію.
- [ ] Автотести проходять; звіт покриття генерується інструментом.

## Перевірка
Із кореня репозиторію:

```powershell
dotnet test backend/SolarFlow.Api.Tests/SolarFlow.Api.Tests.csproj --collect:"XPlat Code Coverage"
dotnet ef migrations has-pending-model-changes --project backend/SolarFlow.Api/SolarFlow.Api.csproj
```

Локальний результат: 13 тестів успішні, незбережених у міграціях змін моделі немає. Перед завершенням issue перевірити ці результати у власному середовищі та під час review.

Тести використовують окремі SQLite БД у пам’яті й не змінюють `solarflow.db`. Звіти покриття створюються в `backend/SolarFlow.Api.Tests/TestResults/`.
